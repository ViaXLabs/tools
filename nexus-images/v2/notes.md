The reason this happens isn't a bug in your script — it's how Nexus's "last downloaded" tracking is built, and it can't tell the difference between a real consumer pulling that image and your report just peeking at its size.

Here's the mechanism: Sonatype's own docs on asset tracking say last downloaded is the date when the asset was last downloaded, updated when it's first downloaded and then on subsequent 200 and 304 responses. That's not scoped to `docker pull` specifically — it fires on _any_ successful response from the endpoint that serves that asset's actual content. So `docker pull`, `docker manifest inspect`, `skopeo inspect`, `syft` scanning straight from the registry, or even a bare `curl` hitting `/v2/<repo>/manifests/<tag>` all count, because they're all real GETs against the same content-serving path. Swapping to a HEAD request doesn't reliably help either — a HEAD still comes back `200`, and the docs describe the trigger by status code, not by HTTP verb. Nexus has no separate "just checking" mode on that endpoint.

The fix is to stop asking the registry protocol for size at all, and get it from Nexus's own metadata database instead — which is a completely different code path that never touches the content-serving handler. This is exactly the `/service/rest/v1/search/assets` endpoint from the reporting design we worked out a few weeks ago: it returns `lastModified`, `blobCreated`, `lastDownloaded`, and `checksum.sha256` straight from Nexus's DB with zero download involved, since it's answering from an index, not serving a file.

The catch, which we flagged back then too: the `fileSize` that endpoint returns for a manifest asset is the size of the small manifest JSON itself (a few KB), not the actual image size people usually mean. To get real image size without paying the "pull" penalty every time, the trick is to only ever pay it **once per unique digest, ever** — because a digest's content never changes, so its size never changes either. Cache it by digest the first time you see it, and every run after that reads the cache instead of touching the registry.

I put together a script that does this:A few things worth flagging as you roll this out:

**The first run still has a one-time cost.** Every image currently in Nexus is an "unseen digest" the first time you run this, so that initial backfill will touch the registry once per unique image (not per tag — duplicate tags pointing at the same digest share one cache entry). After that, as long as you keep `nexus-size-cache.json` around between runs, subsequent runs against those same images are 100% metadata-only. New pushes still cost one small hit each, which is unavoidable — you have to learn a new image's size somehow.

**If you're also running an SBOM/vulnerability scan against the registry** (the syft-based script from a while back), that's a separate problem this doesn't fix — an SBOM scanner genuinely needs to unpack layer contents to see installed packages, so there's no metadata-only substitute for it. If that scan runs on the same schedule as your size report, it's likely contributing to the "images never age out" symptom too, independent of the size question.

**Worth a conversation with whoever owns the cleanup policy:** any policy keyed on "last downloaded before N days" is permanently exposed to this class of problem — the docs describe it updating on any successful 200/304 when the asset is first downloaded and then on subsequent 200 and 304 responses, with no way to exempt a particular tool or user. A vulnerability scanner, a promotion job, or a curious developer running `docker pull` to check something will reset the clock just as effectively as your report did. If the real goal is "roll off things nobody actually deploys," a criterion like "published before" or "last blob updated before" (age since push, not read activity) is immune to this entirely — the trade-off is it'll also age out an old image that's still being quietly pulled by something, so it's a different definition of "unused," not a strict improvement.
